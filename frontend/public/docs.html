01 — What it is

Describe the data you want, get a working scraper

You give it a URL, a JSON schema and a plain-English prompt. It looks at the page with a real browser, asks a model to write a Playwright extraction script, runs that script in a sandbox, validates what came back, and — when the first draft fails, which is often — feeds the error back and tries again. You get the data and the script that produced it.

On top of that sits a broker directory: a list of 67 mortgage companies imported from a spreadsheet. Press Generate scripts once and a model writes a scraper per site. Press Run all whenever you want fresh data and it replays those scripts, merging every loan officer it finds into one table keyed on NMLS licence number.

The retry loop is the product. First-shot LLM scrapers break on real sites constantly — dynamic class names, lazy-loaded content, a cookie banner over the button. Everything else in this repo exists to make that loop cheap to run, safe to run, and honest about what it produced.
02 — How I write code here

Ten habits, and what each one cost when I skipped it

These are not aspirations. Each is here because breaking it produced a specific, traceable problem in this repo — and the example under each one is that problem.

01

Read the whole flow before the first edit

Trace every file the change touches, end to end, before choosing an approach. The smallest diff in the wrong place is not efficiency, it is a second bug wearing efficiency's clothes.

The batch feature looked like it needed its own execution path. Reading retry_loop.py first showed that run_job(id, script=saved) already was that path — so “a manual run never calls the model” needed zero new code.
02

Climb the ladder; stop at the first rung that holds

Does this need to exist at all? Is it already in the codebase? Does the standard library do it? A native platform feature? An installed dependency? Can it be one line? Only then write something.

.env loading is eight lines of stdlib instead of python-dotenv. Dedupe is a generated column plus a unique key instead of application code. The theme toggle is prefers-color-scheme, not a library.
03

The comment says why, never what

The code already says what. A comment earns its place by recording the alternative that was rejected and the reason — that is the thing a reader six months out cannot reconstruct, and the thing that stops someone “simplifying” a load-bearing decision.

# Table-qualified on the right: `new` aliases the same table, so a bare column name in here is ambiguous, not the existing row.
04

A deliberate shortcut is marked, with its ceiling and its exit

Corner-cutting is fine. Silent corner-cutting is not. Every knowing simplification carries a ponytail: marker naming the limit it accepts and what to do when that limit is reached, so “later” has an address.

# ponytail: one company at a time, in-process. 67 sequential Playwright runs is minutes, not a queue problem — revisit when the list is thousands long.
05

Non-trivial logic leaves exactly one runnable check

Not a suite, not fixtures of fixtures — the smallest thing that fails if the logic breaks. And test the failure paths first: timeout, non-JSON stdout, schema mismatch, empty result. Those are the ones that actually fire.

test_a_manual_run_replays_the_saved_script_and_never_generates is one assertion that run_job was called with a script — the whole “Run all cannot cost money” promise, in one line.
06

A guard ships with both halves of its corpus

Anything that rejects input needs a list of what it must reject and a list of what it must let through. The second list is the important one: a rail with only the first is one false positive away from breaking everything it was meant to protect.

KEEP holds a two-digit licence from the early registry, a surname containing the banned word “next”, and an officer known only by a licence number. DROP holds the button, the heading, the cookie banner.
07

One guard at the one door, never one per caller

Find the single function every path routes through and put the check there. It is a smaller diff than a guard in each caller, and it fixes the callers the ticket never mentioned.

check_script lives inside executor.execute, so a script replayed from the cache is checked too. check_officer lives inside upsert_officers, the only way a row can reach the table.
08

Errors surface verbatim, and never as “something went wrong”

No bare except: pass, no broad catch that hides a non-retryable 400. When a provider explains itself in a response body, that body reaches the user. A test walks the whole package asserting this.

A 503 from an overloaded model is survivable and steps down to a smaller one. A 400 saying model does not exist is not, and fails the job with those words in it.
09

Make the invariant machine-checked, not documented

A rule that lives only in a markdown file decays. If it can be an assertion, an AST walk or a database constraint, it should be — then it fails on the pull request instead of in production.

test_hardening.py walks every module's imports against the architecture table and fails on a new file with no row in it. Moving the evals into the package bought them two enforced rules for free.
10

Calibrate on real data; paper reasoning gets thresholds wrong

A number chosen from first principles is a guess. Run the thing against reality, look at what came back, and move the number — then write down what the data said so the next person does not undo it.

I allowed 1–8 digits for a licence number as “generous headroom”. Real scrapes let 15338206 through: a genuine seven-digit id with a stray digit. Tightened to 7, with the upgrade trigger written in the comment.
03 — The shape

Grouped by feature, with the boundaries enforced by a test

Each feature owns its whole vertical slice — routes, validation, persistence, orchestration. Features never reach into one another sideways. Three leaves sit outside all of them, and anything may import a leaf.

Decision

Group by feature, not by layer

The alternative

The conventional layout: models/, services/, repositories/, routers/. Every feature smeared across four directories.

What I chose

A package per feature owning its own router, schemas, db and logic. Adding a feature is a new directory plus one include_router line.

Because the boundaries that actually matter here are not layers — they are capabilities. “Only scraping/ may open a browser” and “only llm/ may call a model” are statements a layered layout cannot even express, and this one enforces with a test.

04 — The self-healing loop

Four ways in, one way through, and a number that means something

POST /jobs returns a job id immediately and the work happens behind it. What happens depends entirely on what the caller already had.

Decision

Generate a persistent script, don't run a live agent

The alternative

An agentic loop: the model decides every click in real time. More flexible, handles anything, needs no repair loop.

What I chose

One model call produces a script. The script is saved and re-run for free, for ever, until the page changes under it.

A live agent costs a model call per navigation step, on every run. Here the cost is paid once at generation and the marginal run is zero — which is the only reason “re-scrape 67 directories” is a button somebody can press casually. The price is that first drafts fail, and that price is exactly what the repair loop buys back.

05 — The broker directory

Two buttons, because they cost different things

67 companies came out of a spreadsheet whose header row is misaligned — “Method” sits one column right of its values — so the importer reads by position, not by name. When that column holds a URL it becomes the directory to scrape; when it holds Search Button it becomes a hint appended to the prompt.

Decision

Two buttons instead of one

The alternative

One Run all that generates a script for any company missing one, then runs everything. Fewer clicks, nothing to explain.

What I chose

Generate scripts is the only control that can reach a model. Run all replays and reports what it skipped.

Run all is the button somebody presses on a schedule, possibly for years. A control with an unpredictable cost is a control people stop pressing. Splitting them makes one button boring and safe, and confines the expensive, interesting one to a deliberate act.

A single row can be generated for too — the Generate link beside Details — but that is the same POST /companies/scripts with ids of length one, not a per-company route. It takes the same lock, reports through the same progress line, and asks first, because it is the same expensive button pointed at one site.

06 — One row, one officer

Two clocks, a generated key, and never overwriting something with nothing

The output is a table of loan officers: name, licence number, email, phone, address, position, the page it came from, when it was first seen and when it last changed. Getting “last changed” to mean anything is most of the design.

Whitespace

Collapsed, not stripped

Real pages are full of &nbsp;. Jane\xa0Doe and Jane Doe are one person with two different keys — a duplicate officer the first time the site changes its markup.

Empty values

Never overwrite with nothing

The repair loop rewrites scripts, so script quality varies between runs. A run that missed the email must not delete the one the last run found.

Milliseconds

TIMESTAMP(3), not TIMESTAMP

Two passes of the batch can land in the same second. At second resolution “when updated” cannot tell them apart, and the test that proves the clock moves cannot pass.

07 — The three rails

Two are about safety. The third is about truth.

Three artifacts in this system were written by someone outside the repo, and each gets a deterministic rail at the single place it enters. No rail is a model judging another model — that would cost a call per job to answer a question a parser answers exactly, instantly, and without an error rate of its own.

What the third rail actually caught

This is not hypothetical. The first live scrape of a real broker directory put 24 officers in the database. Eleven of them had licence numbers like 94318402079631. The page reads: 

NMLS# 943184 / CA DRE# 02079631

# the script stripped non-digits from the whole line and ran two
# different licences together. 943184 is the mortgage licence.
# 02079631 is a California real-estate licence. Nobody has 94318402079631.

Every one of those rows passed schema validation, because a string is a string. They were stored as fact. The rail now rejects the whole row rather than repairing the field — a mis-parsed licence means the script read the wrong container for that card, so the address and phone beside it are suspect too, and half a person in a database looks exactly like a whole one.

The rail alone was not enough, and that was a real bug in my first design. Dropping the row at the database door left the saved script producing schema-valid output for ever — so the next Generate pass would replay it, call it a success, and never fix anything. Handing the rail into the attempt is what turns a wrong extraction into a repairable failed attempt. Watching that chain fire end to end is what found it.

Calibrating on the data, not on paper

I first allowed 1–8 digits for a licence number, reasoning that the registry is at seven digits and eight was generous headroom. The next real scrape let 15338206 through: a genuine seven-digit id with a stray digit run onto the end, indistinguishable by shape until the range is tight. Tightened to seven, where all 24 clean rows and all 67 companies sit — with the upgrade trigger written into the comment, because the cost of being late is one rejected row and one repair, and the cost of being loose is a fabricated licence stored as fact.

Decision

Deterministic rails, not NeMo Guardrails or a judging model

The alternative

A guardrails framework, or a second model asked “is this script safe? is this row a real person?”

What I chose

An ast walk, an ipaddress check and a handful of regexes. Roughly 200 lines, no dependency.

NeMo resolves to 56 packages here — langchain, SQLAlchemy, pandas, numpy — and its rails are model calls against a dialog runtime. This app has no dialog; the risky artifact is a Python file and a table of strings. A syntax tree answers “does this import anything?” exactly, in a millisecond, for free, and is never having a bad day. A model-based rail would add a call, its latency and its own error rate to every single job.

08 — The evals

The tests prove it runs. The evals ask whether it is right.

Five cases, each a local page plus the exact rows a correct scraper returns from it. The bar is exact: five of six products is a failure, and so is "$129.00" where the schema said number.

CaseWhat it measuresLatest
flat-listright container, currency coerced, a missing field as None6/6 · 1 att
paginationfollows “next” once and stops at the end instead of looping8/8 · 1 att
first-fourstops at the count asked for — over-fetching is a failure too4/4 · 1 att
loan-officersthe real production prompt against a realistic directory4/4 · 1 att
detail-pagescollects hrefs before navigating, then visits each detail page4/4 · 1 att

The loan-officers case is the one that measures production. It imports the real OFFICER_PROMPT and OFFICER_SCHEMA the broker batch actually sends rather than a copy — an eval against a copy measures the copy. Its fixture site has what real directories have: details only on the profile pages, an officer with no licence number anywhere (the model must leave it blank, not invent one), &nbsp; in a name, and a “Load More” tile that a slightly-too-broad card selector picks up as a person.

The report also counts what each rail did to real model output. On a case that scored ok, every rejection is a false positive — and a false positive there is 67 empty companies that look like a working scrape.

Decision

In the package, but forbidden the database

The alternative

Leave evals/ outside backend/, since it is a development tool and not part of the served app.

What I chose

Move it in, and give it two rows in the import table: it may not name a database, and may not import retry_loop.

Being inside buys those two rules a machine that enforces them. Both guard the same mistake: the real loop replays a saved script when the URL, prompt and schema match, and an eval that could do that would be scoring the cache instead of the model — silently, and in the flattering direction. The eval deliberately re-implements the loop without the replay; importing the real one would quietly put it back.

09 — The frontend

Vite, React, zustand, and no fourth thing

Three pages: submit a job, manage the broker list, browse everything. style.css is the design system; there is no UI kit and no router.

No router

page is a store key

Three views, switched through zustand and persisted, so a refresh puts you back. Add react-router the day these need shareable URLs — and move page out in the same change rather than keeping both.

Persistence

What you made survives; what was fetched does not

Draft, page, theme, browse tab, open rows and the watched job's id. Never rows or job state — a cache that outlives the page shows yesterday's data as though it were now.

Subscriptions

Components subscribe to fields, not the store

useStore(s => s.draft.url), never useStore(). A selector returning a fresh object re-renders on every action; a keystroke in the prompt box should re-render the prompt box.

Editing

The cell is the control

No edit mode, no save button. Blur or Enter saves, Escape puts back what was there. The table reloads every two seconds during a batch, so a cell re-syncs only when the stored value changed — never mid-keystroke.

Errors

The 422 body, verbatim

Whatever the API said appears on screen exactly. Swallowing it is how you get “something went wrong”, which tells a user nothing and a developer less.

Safety

Never dangerouslySetInnerHTML

Everything on the page is scraped third-party text or a model-written script. React escaping it by default is the entire XSS story for this app.

A real bug this section exists to remember. CORS allowed only GET and POST, while the rename used PATCH — so renaming a job silently failed in npm run dev, where the page and the API are separate origins, and worked in the built bundle, where they are not. Found by adding PUT and DELETE and reading the line properly.

Everything the frontend can ask for

MethodPathWhat it does
POST/jobsCreate a job. Optional script runs that code instead of generating one. Returns an id at once.
GET/jobs/{id}Poll. Echoes the three inputs back, so a client holding only an id can re-run it.
PATCH/jobs/{id}Rename. The only mutable field — the other three are the reuse key.
GET/jobs/{id}/attemptsEvery attempt for one job, in order. What the model actually wrote.
GET/jobsEvery job, newest first.
GET/attemptsEvery attempt across all jobs.
GET/scriptsSaved scripts available for reuse, with a reuse count.
GET/companiesThe broker list, with each one's officer count and last run.
POST/companiesAdd a broker. URLs go through the same rail as /jobs.
PUT/companies/{id}Replace the editable columns. A full row, not a patch.
DELETE/companies/{id}Remove a broker and, by cascade, its officers.
POST/companies/scriptsWrite a script per company without a working one. The only route that can call a model.
POST/companies/runReplay every saved script and merge the officers. 409 if a batch is going.
GET/companies/runProgress. running is the runner's lock itself, not a flag beside it.
GET/officersScraped officers, most recently changed first. Read-only.
GET/health{"ok": true}

422 means the input was rejected at the boundary. 503 means the database is unreachable — a retryable answer, not a stack trace. Anything else that goes wrong becomes a failed job carrying the real error, because a broken scrape is a result, not an HTTP error.

11 — Deliberately absent

The list of things that are missing on purpose

Every one of these is a decision, not an oversight. Each needs a measured reason before it gets built — “it might scale later” is not one.

Not hereWhy not, and what would change my mind
Redis / Celery / a brokerFastAPI background tasks run one job at a time, which is what this needs. A measured throughput bottleneck.
DockerNothing here is hard to run locally. Deploying to more than one machine.
Auth / rate limitingIt runs on a dev box. The moment the port is reachable by anyone else.
Concurrency in the batch67 sequential Playwright runs is minutes. A list in the thousands.
A schedulerRun all is a button somebody presses. Wanting it nightly without anyone present.
Editable officersThe next run merges over them, so an edit would vanish silently. It needs a manual flag the upsert skips — deliberately, or not at all.
Cache invalidation / TTLA saved script is retired by failing a replay, which is the honest signal. Scripts going stale without failing.
Login-walled sitesA 401 or 403 fails the job saying so, rather than feeding a bot wall to a model.

Verified against a live MySQL 8.0.33 and real broker sites: 209 Python tests, 38 store tests, 5 of 5 eval cases correct on the first attempt, 67 companies seeded and 24 loan officers extracted, deduplicated and clean. The two findings that shaped this document — the concatenated licence numbers and the rail that could not reach the attempt — both came from running it, not from reading it.
